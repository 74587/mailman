打开触发器管理

从 0 到 1 创建第一条规则

目标：当 GitHub 登录验证码或安全提醒进入邮箱时，自动给邮件加标签，推送 Webhook，并把关键信息转发给运营邮箱。你可以先在 UI 完成，再把同样配置交给外部系统通过 API 创建。

1
准备账户
先在“邮箱账户与 OAuth2”中接入至少一个邮箱，并完成验证。触发器只会处理已经同步进 Mailman 的邮件。
2
进入触发器管理
菜单：自动化 → 触发器管理。点击创建入口后填写名称，例如“GitHub 安全邮件处理”。
3
配置条件
先选 group 作为根表达式，operator 选 and。子条件用发件人包含 github.com、主题包含 security 或 verification。
4
测试条件
使用测试邮件数据调用 POST /api/v2/triggers/test-condition。返回 result: true 再继续配置动作。
5
编排动作
推荐顺序：变量提取 → 打标签 → Webhook → 转发。每个动作都有 executionOrder，数值越小越先执行。
6
保存并启用
保存时 enabled 可以先设为 false，确认测试通过后调用 POST /api/triggers/{id}/enable 或在 UI 中启用。
7
观察日志
上线后看 /api/triggers/logs、/api/triggers/{id}/statistics，重点关注失败动作、耗时和最后错误。

触发器数据模型

触发器由一个或多个表达式和一个动作数组组成。表达式负责“是否命中”，动作负责“命中后做什么”。动作默认按 executionOrder 顺序执行，禁用的动作不会执行。

EmailTriggerV2

创建请求字段：name、description、enabled、expressions、actions。响应会额外包含 id、执行计数、最后执行时间和最后错误。

{
  "id": 12,
  "name": "GitHub 安全邮件处理",
  "description": "识别安全提醒并通知业务系统",
  "enabled": true,
  "expressions": [],
  "actions": [],
  "totalExecutions": 128,
  "successExecutions": 126,
  "lastExecutedAt": "2026-05-31T10:12:30Z",
  "lastError": "",
  "createdAt": "2026-05-30T08:00:00Z",
  "updatedAt": "2026-05-31T10:12:30Z"
}

TriggerExecutionLogV2

日志用于复盘每次执行：条件是否命中、每个动作是否成功、耗时、错误、输入输出和 trace。排查时先看日志，再看后端运行日志。

GET/api/triggers/logs?page=1&limit=20执行日志列表
GET/api/triggers/{id}/logs某条规则日志
GET/api/triggers/logs/stats全局日志统计
GET/api/triggers/{id}/statistics单规则统计
字段位置说明常见错误
id表达式、动作前端和日志定位使用，建议稳定唯一。测试动作时缺少 Action ID 会被拒绝。
operator表达式组合条件可用 and、or、not；普通条件可用 contains、equals 等比较符。把组合运算符和字段比较符混用。
pluginId表达式、动作插件 ID 必须和内置注册表一致，例如 webhook_action。把插件显示名写进 pluginId。
config动作动作插件配置对象，各插件字段不同。Webhook 的 headers 写成对象而不是数组时，需确认当前执行器是否兼容。
enabled动作、触发器触发器和动作都有启用状态。触发器启用但动作被禁用，日志中看似命中却没有效果。

表达式：决定邮件是否命中

表达式数组会被后端组合成根条件进行计算。最稳妥的写法是只放一个根 group，再把所有子条件放进 conditions。

类型用途核心字段适合场景
group组合多个子条件operator、conditions同时满足、任一满足、取反。
condition直接比较邮件字段field、operator、value、not主题、发件人、正文、收件人、附件等简单判断。
plugin调用条件插件pluginId、fields账户集合、邮箱前后缀、时间范围、大小范围。
expression自定义表达式fields.engine、fields.expression普通条件表达不了的计算逻辑。

发票附件

组合不同能力实现复杂效果

动作链不只是“命中后发通知”。变量、AI、分支、并行和中断组合起来，可以让邮件变成业务流程的一部分。

线性处理

提取验证码 → Webhook 回传 → 打标签。适合验证码取件、工单通知、账单归档。

AI 后分支

AI 判断风险等级，低风险只打标签，高风险同时发 Telegram 和 Webhook。

并行加速

Webhook、Telegram、转发同时执行。配合 ignore_errors 可以防止一个通知失败拖垮全部流程。

排查手册

条件没有命中

先用 /api/v2/triggers/test-condition 放入真实邮件字段测试。常见原因是字段名写错、同步后的正文是 TextBody 而不是 Body、发件人字段取的是 FromAddress 而不是展示名。

动作没有执行

检查触发器 enabled 和动作 enabled，再看 executionOrder 是否符合预期。测试动作时必须带 id 和 pluginId。

Webhook 返回失败

确认 success_condition 和期望状态码。若目标服务在内网，配置 proxy_enabled、proxy_type、proxy_host、proxy_port。

上线后重复触发

检查同步策略、时间范围条件和邮件去重字段。验证码或通知类邮件建议加 email_time_range 或取件模板中的等待窗口。

最小排查材料：触发器 ID、邮件 ID、日志 ID、动作 ID、插件 ID、测试请求体、后端日志时间段。把这些信息凑齐，基本就能定位到条件、插件配置或外部服务三类问题之一。
